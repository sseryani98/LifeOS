# Fiori Elements testability: "ours" is the extension surface plus the behaviour our annotations promise; SAP tests both through journeys, not unit tests

**In a Fiori Elements (FE) app, the code that is "ours" is small (controller extensions, custom actions/sections/fragments, formatters, manifest + annotations), but the behaviour that is ours is large, and SAP's own guidance and reference app cover that behaviour almost entirely through OPA journeys built on `sap.fe.test`, with no unit tests on extensions at all.** What holds: SAP explicitly draws the line at "the library tests framework behaviour, you test application-specific functionality", which maps onto the "never test the framework" standard. What does not hold: the prior assumption that near-zero logic means near-zero testing — annotation-driven behaviour (which fields are editable in which state, which actions are enabled for which selection, draft/save flows with custom validation) is the module's own contract and SAP's reference journeys assert exactly that. The cost is that this coverage lives at the journey tier, which is the tier where coverage instrumentation and `npm test` integration are hardest (see `gate-integration`). What would change the answer: a documented SAP pattern for unit-testing a `ControllerExtension` outside the framework — searched, not found.

**Mode:** Ground · **Verdict:** none (Ground) · **Confidence:** Medium · **Feeds:** Testing philosophy (Test Strategy amendment) · **Researched:** 2026-11-04 · **Status:** Draft

## SAP's own line between "framework" and "ours" is the ExtensionAPI boundary

**SAP documents a hard boundary: extension code may use only the public `ExtensionAPI` and public `Controller` methods, and anything FE creates (controls, models, bindings, underscore-prefixed members) is framework-owned and unsupported.** The SAPUI5 documentation page "Using the ExtensionAPI" (OData V4, sap-docs/sapui5 `using-the-extensionapi-bd2994b.md`, fetched 2026-11-04) states that extension hooks and handlers should use only public `sap.ui.core.mvc.Controller` methods and must not access or change controls, properties, models or objects the framework creates. Every extension-point page (custom columns, custom sections, custom actions, forms) repeats the caution that after an extension is created, "its display ... and system behavior (for example, model and binding usage, busy handling) lies within the application's responsibility" (Documented, same docs set). That sentence is the testing contract: whatever an extension renders or does is ours to test; whatever FE renders from annotations is the framework's to render but ours to _specify_ — and SAP's test library exists so we can assert the result without touching FE internals.

The SAP developer tutorial "Write OPA Tests for an SAP Fiori Elements for OData V4 Application" (developers.sap.com `fiori-tools-mockserver-opa-testing`, fetched 2026-11-04) says it directly: the library "tests framework behavior, so you only need to test application-specific functionality", and it then lists what the app developer should still test — row counts, filtering, select-and-delete with dialog confirmation, navigation to the object page, header and form field checks, edit/save, back navigation (Documented). Note that most of that list is annotation-driven behaviour, not custom code.

## Annotation-driven behaviour counts as "ours", and SAP's reference journeys treat it that way

**The "never test the framework" rule forbids asserting _how_ FE renders an annotation; it does not forbid asserting _that_ our annotation produced the behaviour we specified.** The distinction is observable in cap-sflight: `iCheckRows({Travel:"4,132","Travel Status":"Open"},1)` followed by `iExecuteAction({service:"TravelService",action:"acceptTravel"})` and `iCheckRows({... "Travel Status":"Accepted"},1)` asserts the app's own action and field-control annotations plus its CAP handler, through FE, without touching any FE control (Verified). The `sap.fe.test` API is designed around semantic identifiers — `{property}`, `{service, action}`, `{section, fieldGroup}` — precisely so the test names the app's contract rather than FE's control tree (Documented, d.ts: `FormActions.iChangeField`, `TableAssertions.iCheckAction`, `HeaderActions.iExecuteAction`).

Inferred: in Life OS the annotations live in CAP `.cds` files beside the service, so a slice of this behaviour (field control, action availability, draft rules) is also assertable at the CAP tier with Jest against OData, which is cheaper. Which assertions belong on which side is a design decision for the amendment; SAP's samples put the _user-visible_ consequence on the journey side.

## SAP's reference app runs FE journeys headless against a real CAP server, not a mock

**cap-sflight (SAP's canonical CAP + FE sample) has no QUnit for its UI, and runs its `sap.fe.test` journeys through Karma with `karma-ui5` 4, `karma-ui5-transpile` (for TS), Puppeteer-headless Chrome, and a custom Karma middleware that spawns `cds serve` on a random port and proxies to it** (Verified: `app/.karma/karma.conf.js`, `app/.karma/karma-cap-middleware.js`, `app/travel_processor/package.json` `"test:node": "karma start --server=node --single-run"`, `.github/workflows/node.js.yml` running `npm run test:node -- --ci` per app). The journeys start with `Given.iResetTestData()`, a `sap.fe.test.BaseArrangements` arrangement whose protected `resetTestData()` the docs say "can be overwritten to add custom clean-up functionality" (Documented, d.ts lines 3031–3073). This is a Reported-grade practice signal (SAP sample, not a documented recommendation), and it conflicts with the brief's statement that Karma is retired — flagged to siblings below.

## Prior assumption, graded

"Near-zero logic in FE apps → little to unit-test": **holds for the unit tier, refuted for coverage as a whole.** Holds: in cap-sflight and in Life OS's three FE apps the unit-testable surface is formatters, shared utilities, base classes and custom controls — all in `shared/`. Refuted: the behaviour surface (what each ListReport/ObjectPage does under our annotations, plus two controller extensions) is where production-grade coverage lives, and SAP places it in the journey tier. A coverage threshold expressed only as unit-line coverage would measure `shared/` and tell nothing about the 32 FE page targets (Inferred).

## What we could not establish

- **Whether a `ControllerExtension` can be unit-tested outside the framework.** The public constructor is `@ui5-protected` and `base` is not in the public type (`@sapui5/types@1.136.0` `sap.ui.core.d.ts` module `sap/ui/core/mvc/ControllerExtension`); cap-sflight augments the module with a local `ControllerExtension.d.ts` declaring `base.getExtensionAPI()`. Searched Context7 (`/sap-docs/sapui5`, `/ui5/docs`) for "unit test controller extension ExtensionAPI" — no SAP page found. Settling check (needs disk/runtime): in a QUnit page under the UI5 bootstrap, `new AdminMasterDataExtension()` then assign `ext.base = { getExtensionAPI: () => fake }` and call `ext.override.editFlow.onBeforeSave()`; if the constructor throws or `overrides` is not reachable as instance methods, the hook logic must be extracted into a plain function to be unit-tested.
- **Whether `sap.fe.test` page objects (`appId` + `componentId`) resolve when the FE app is hosted as a component inside the freestyle `shell/` ToolPage rather than under `index.html`/FLP sandbox.** Both SAP samples launch via `launchUrl` to the app's own `index.html` or `flpSandbox.html`. Settling check: a one-journey spike with `launchUrl` pointing at the shell route and `iSeeThisPage()` on one ListReport.
- **How stable FE-generated IDs for custom sections are across 1.136.x patches.** cap-sflight hard-codes them; no SAP statement on stability found. Settling check: diff the ID after the next minUI5Version bump.
- **What `iResetTestData()` does by default** (the d.ts only documents the override hook). Settling check: read `sap/fe/test/BaseArrangements-dbg.js` from the installed 1.136.16 resources.

## Implications for design

1. **Define "ours" in the amendment as: (a) every TS file under `app/**` and (b) every user-visible behaviour the module's annotations and manifest promise.** (a) is coverable by instrumented unit/journey code; (b) is coverable only by journeys and is not a line-coverage number.
2. **Unit tier = `shared/` (utils, base classes, custom controls, formatters).** This is where a coverage threshold is meaningful and where `qunit-unit-tests` and `gate-integration` findings apply directly. Expect it to be the only place a per-file percentage makes sense.
3. **Journey tier = one `sap.fe.test` journey set per FE app**, with at minimum: smoke (`iSeeThisPage` on each target), one annotation-contract journey per page (field editability / action enablement / filter default), and one journey per controller extension hook that drives the hook through its FE entry point (save, delete, navigate). Follow cap-sflight's shape: `JourneyRunner` + `ListReport`/`ObjectPage` page objects with `AdditionalCustom...Definition` reserved for app-specific actions.
4. **Decide explicitly where annotation behaviour is asserted**: user-visible consequence in the journey, data rule in the existing Jest/CAP tier. Do not assert both for the same rule; that is the "testing the framework" trap in disguise (Inferred).
5. **FPM custom page, `csv-import-wizard` and `shell` are outside `sap.fe.test`.** The amendment needs a second journey mechanism for them — the choice is owned by `opa5-journeys`, `wdi5-e2e` and `playwright-in-repo`. One consequence: Project Tracker's "no in-repo frontend suite" (D-195) cannot be reversed with `sap.fe.test` alone, because its page is FPM.
6. **Journey data setup is a design item**: SAP's `iResetTestData()` pattern against a real CAP server, not a mock server, is the reference shape, and it aligns with the existing `functional-tester` agent's real-Postgres approach. Whether the gate owns a reset endpoint or reuses the FUT fixture belongs to `gate-integration`.
7. **If the question had been asked differently**: "what coverage _number_ is achievable for FE apps" is the wrong question; "which behaviours must have a journey before a story closes" is the one the amendment should answer, with line coverage reserved for `shared/`.

### Cross-topic flags

- `qunit-unit-tests`: cap-sflight (Oct 2026) still uses `karma-ui5` 4 + `karma-ui5-transpile` + Puppeteer headless, which contradicts "Karma is retired" as a premise; confirm the status of `karma-ui5` versus `@ui5/test-runner` before the verdict. Also: `ControllerExtension` has a protected constructor and no public `base` type — unit-testing extensions is unproven.
- `opa5-journeys`: `sap.fe.test` is alive and TypeScript-typed in 1.136 (`@sapui5/types` ships `sap.fe.test.d.ts`); it is the FE-specific journey toolkit, but it has no page object for FPM custom pages (only `ListReport`, `ObjectPage`, `Shell`).
- `wdi5-e2e` / `playwright-in-repo`: the FPM page, `csv-import-wizard` and `shell` need a non-`sap.fe.test` mechanism; the custom-section IDs are FE-generated (`...fe::CustomSubSection::<key>--<id>-content`).
- `gate-integration`: SAP's reference CI spawns `cds serve` from inside the test runner and proxies; the journeys assume a resettable backend (`iResetTestData`).
